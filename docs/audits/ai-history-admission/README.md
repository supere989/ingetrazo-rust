# Retained append history admission

The private standalone owner now tracks retained delta payload bytes with constant-time undo/redo counters. A configurable limit checks the projected undo branch before semantic publication. Rejected new branches leave the old redo history, mesh, state token and accounting intact. Undo/Redo transfer the existing charge between stacks, including when a host lowers the limit below already-retained history. The limit does not evict existing commands. Successful replacement clears their charges.

The charge includes Delta records, the actual capacities of retained vertex/edge vectors, and each retained new-vertex adjacency vector. It excludes allocator overhead, the history stack vectors' capacity slack, live mesh, cold source lookup, preparation scratch and VM allocations. Thus this is a retained-command payload admission limit, not total process memory or comprehensive OOM handling. Delta clone preparation now uses fallible reserves for records and adjacencies; metadata-bearing edges are refused by this append-only owner rather than copied with hidden allocations. No production admission is enabled.

The focused test covers rejection with an existing redo branch, exact stack charge transfers, a new-command rejection on the live branch, retry after lifting the limit and replacement release. The real Rust allocator probe reuses the existing 10,000-vertex/96-command design because retained record preparation changed: requested live allocation grows 62,487 bytes; charged retained delta payload is 36,864 bytes; 96 Undo and 96 Redo succeed; replacement releases 1,635,088 requested bytes. These counters measure requested Rust allocations, not RSS or allocator fragmentation. O(base) cold lookup/index preparation and remaining pre-mutation infallible allocations are still explicit prerequisites; staging admission is separate.

The source/original command-history oracle is unchanged and its retained evidence was reused. No broad suite or external provider call ran.
