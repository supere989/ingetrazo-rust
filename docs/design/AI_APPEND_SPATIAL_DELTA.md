# Reversible native spatial-index publication

The full original scripting objective remains unchanged. This stage improves only the private append-owner prerequisite; no production interpreter activation or full scene adapter claim.

The former commit/Undo/Redo path allocated an ordered base-coordinate copy and rebuilt the whole native HashMap each operation. Constructor and replacement still prepare the exact whole index, but append publication now prepares an O(changed vertices) patch: appended positions plus one tuple per unique native PointKey containing predecessor mapping and final appended ID. The native PointKey law is intentionally independent from the Qt-compatible BigInt source registry. Native collisions—including several appended vertices sharing a key and a duplicate-key imported base—restore the exact previous mapping on Undo.

Preparation fallibly reserves ordered positions, key records, temporary deduplication map, and live spatial-map capacity before semantic writes. Private owner state/version rejects stale transactions; publication verifies changed positions and affected predecessor mappings. Undo validates changed tail and final mapping before any semantic write, restores predecessor mappings without allocation, and immediately truncates records. Redo checks predecessors and reserves map capacity before copies/publication. The patch is owned by the command delta and charged in history payload. No hidden full base coordinate/index clone remains in these operations.

The API requires an exclusive append owner preserving untouched prefix and exact tail ownership; it is not a general validator of public Mesh mutation. Full constructor validation remains cold. Source registry truncate relies on a separate invariant: source-weld append never publishes a duplicate SourceKey, so removal cannot replace a source predecessor. Native index keys can collide and therefore need explicit predecessor tuples.

Registry positions now use amortized reserve rather than exact resize per append. Vector/hash table growth may occasionally allocate/copy proportional to capacity; this is reported, not hidden. The focused scaling fixture preallocates live Mesh vectors and primes one registry capacity expansion before measuring warm operations. Initial growth at 50,000 vertices is retained separately. No worst-case constant-time allocation claim, physical allocator cap, arbitrary operation atomicity, or whole Python memory/deadline claim follows.

Evidence: four actual allocator-null injections at each index preparation allocation site, retry/restore; collision/stale/nonfinite controls; owner refusal/Undo/Redo/stale-token controls; 12 original history states and seven registry-backed source weld cases; actual allocator growth at 1,000 vs 50,000 base vertices across 64 append+Undo+Redo commands. Full operations, live app ownership routing, compiler/native bounds and full imports remain required.
