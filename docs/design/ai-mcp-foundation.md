## Transaction ownership: advertised vs operative original

run_transactional uses eval then exec fallback, persistent scope{viewport,scene/model,mesh,selection,groups,layers,bim,QVector3D,Mesh,Group,Vertex,Edge,Face,recipes}; expression values printrepr and update _. stdout/stderr captured; traceback/error rollback; one undo step per changed script; inspect-only restores savedredo. Recipe helpers revolve/extrude/prism/wall/house construct deterministic engine geometry, orient/soften and append groups.

Actual SnapshotImport snapshots only loose mesh and tracks appended groups,layers,savedviews,dimensions,textlabels. Existing group/global presentation/material/terrain/image edits and removals are not covered by that rollback or unchanged detection. This is a retained source limitation, not an acceptable whole-document atomicity guarantee. Before native arbitrary execution, every exposed mutable object/list/field must be journaled: lazy first-write ownership snapshots, staged newly-created resources and identity-preserving rollback; one committed action through source-aware history, no history entry/redo loss for reads. Avoid fullScene cloning on hot paths. A limited typed action interpreter must never be called run_python parity.

## Arbitrary Python feasibility remains OPEN

RustPython supplies an embeddable Rust VM/native module interface, but its own project documents development/production readiness limits: [RustPython README](https://github.com/RustPython/RustPython), [embedding API](https://docs.rs/rustpython/latest/rustpython/). Candidate native bindings would implement Python-visible CAD/QVector3D semantics with Rust-owned handles/proxies and native recipe modules; tests must cover imports, attribute/list mutation, f32Qt quantization, shared object identity, eval/exec, stdout,exceptions, persistent variables and undo lifetimes. A CPython shared-library embedding is a separate compatibility option, not Rust-native interpreter proof. Neither option is implemented or proven here; no subprocess interpreter wrapper is proposed. Original PySide/core arbitrary imports cannot be assumed compatible merely because syntax evaluates. Full original scripting scope, recipe book/BIM, MCP tools and atomicity stay explicitly open.
